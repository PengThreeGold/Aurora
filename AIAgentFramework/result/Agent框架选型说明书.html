企业级 AI Agent 框架选型说明书

版本 2.0 · 整合与复核日期：2026-10-07 · 通用选型，独立于现有业务背景

本说明书帮助架构与开发团队在 LangChain、LangGraph、Google ADK 和 Eino 中选择合适路线。内容覆盖设计、开发、交互、恢复、安全、并发、测试、发布、数据治理、维护与成本。读者可以先完成场景决策，再沿编号查评分理由与证据。

技术路线建议：复杂且需要恢复的流程，推荐 LangGraph 作为编排核心；常规聊天和工具循环，推荐 LangChain；希望统一 Agent 开发与评测，或采用受支持实时语音链路，推荐 Google ADK；明确要求 Go 集成或交付，优先 Eino。 每项建议都有前提和换选条件。性能与生产稳定性的相对优胜结论尚未取得。

阅读路线：决策者先读“范围与场景决策”；架构师读“比较矩阵”与关键能力分析；实现与验收人员读“核心代码”和“采用前验收”。所有完整代码、数据与复现说明均在同目录的唯一附件 Agent框架选型附件.zip 中。

范围与评估基线

本版比较开源框架与明确标出的扩展路径，不代入当前业务的运行时、并发数、数据库或预算。此前的评分与场景指南已经并入本文；读完本文不需要再打开另一个说明文档。

上述是2026-10-06研究时锁定的评估基线，本次整合没有把它们更新成“今天最新版本”。在线文档可能已演进，生产采用时应按锁定组合重新验证。核心包、provider、saver、协议adapter及商业平台有各自版本和许可。

为什么复杂可恢复流程推荐 LangGraph

此处“复杂”有具体含义：存在必须执行的业务校验、明确分支、并行汇总、多次等待用户、进程退出后的继续执行，而不是单纯 prompt 很长或工具很多。这类系统需要把模型决策放在可检查的流程中。LangGraph 的直接图编排、状态管理与持久化契约覆盖这些需求，所以在没有语言硬约束时，本报告推荐它作为默认编排核心。Graph API、Checkpointers、Interrupts。

选择它需要接受两项成本：团队要明确设计 state、节点边界和重试语义；还要建设任务调度、权限、幂等、存储运维和前端接入。LangGraph 不是完整运营平台。如果任务只是问答与工具循环，这些设计可能增加不必要的维护工作，此时 LangChain 更合适。

本地 C07 已验证 LangGraph 的有限恢复路径，因此此建议除了文档还有局部实测依据。但 ADK 和 Eino 没有在本次完成相同恢复实验，不能据此宣称它们恢复更差。选择 LangGraph 的理由是能力与该场景的匹配程度；性能、生产稳定性和整体成本仍未形成比较结论。

采用与换选条件

框架 建议采用的前提 不建议作为默认选择的情况 改变结论的关键证据
LangChain 常规 Agent 循环已满足需求，重视模型/工具接入速度 大量业务逻辑被迫塞进 middleware，状态与顺序已经难以解释 增加 LangGraph 外层流程后，能否明显简化业务分支与恢复逻辑
LangGraph 必须显式控制流程与状态，并愿意维护编排代码 简单任务没有用到图的控制能力；或目标平台不能接受相应运行时 目标数据库恢复、重复操作防护、跨版本任务继续执行是否通过
Google ADK 希望用统一的 Agent、session、eval 路线，或目标实时交互属于已支持范围 必需集成与所选 2.x 路线不兼容；关键能力仅实验性且不能接受变动 精确到 SDK/模型/transport 的兼容测试，以及 Workflow 恢复与升级测试
Eino Go 是实际工程要求，目标模型与工具已有可用 Go 接入 仅凭“Go 更快”选型，但没有性能数据；缺失组件造成大量自建 编译交付、真实存储恢复、目标协议兼容和端到端容量的实际结果

Eino 特定 Workflow Agent 的上下文共享限制已经在 v0.9.21 源码中核对；它应影响协作模式选择，不能扩大成“整个 Eino 不适合企业”。同样，ADK 的图编排已经存在，不能继续用早期能力边界评价当前版本。Eino v0.9.21 Workflow Agent 源码、ADK graph workflows。

从推荐到实际决策

  1. 先确定不能违反的条件。 例如必须 Go、必须离线、指定数据库或指定语音模型；只有真实硬约束才能淘汰路线，不用偏好冒充限制。
  2. 按最主要的任务形态选首选。 普通循环选 LangChain，满足显式流程与恢复前提时选 LangGraph，统一 ADK 开发评测或受支持 Live 场景选 ADK，Go 交付选 Eino。
  3. 为首选指定一个确实可能替代它的备选。 例如复杂流程用 LangGraph 对照 ADK Workflow；Go 工程用 Eino 对照单独核实过的 ADK Go，不把 Python ADK 的分数直接移给 Go。
  4. 用能推翻首选的实验验收。 测试崩溃后是否重复外部操作、权限撤销后能否继续越权、UI 重复提交、升级后的旧任务、资源与时延预算。失败意味着修正组合或换选，不以总分较高为理由放行。

本报告已经给出技术路线结论；生产上线结论需要上述验收。 不计算无场景总分，是为了避免把无关能力加在一起，不是回避推荐。后续可给每种明确场景设置权重，但不能用加权得分抵消权限隔离或业务正确性失败。

决策优先级与可能改变推荐的证据

LangGraph的默认推荐限定在“显式复杂流程、持久恢复、可接受其运行时、团队能维护编排代码”这组条件。本文优先考虑运行状态与恢复边界能否解释和验收，其次考虑集成与交付成本。本地探针增加了对这一组合的有限信心；ADK/Eino未做同场探针，不能由此推断它们更不稳定。

恢复契约有可解释的差异：LangGraph提供super-step与pending writes的保存契约；Eino的该版本图运行以中断保存为主要checkpoint路径，store需实现，恢复需保持图与调用配置一致；ADK resume文档对工具重复、自定义Agent和开发入口给出限制，不能直接等同于所有2.x图的崩溃恢复。选型应验收实际使用路径。

如果ADK Workflow已覆盖目标流程、恢复与升级验收通过，而且统一session/eval减少工程成本，应优先复用ADK。Go硬约束下，若Eino的目标存储与协议验收通过，应优先Eino。没有特殊拓扑时，LangChain可使用相同底层恢复能力，减少起步代码。推荐是可以被这些证据改变的工程决策。S06、S19、S21、S27、S28、S73。

比较方法与评分矩阵

如何解释分数

分数衡量该项能力的工程便利程度。先确认机制或维护中的集成，再看覆盖范围，最后列应用必须完成的工作。数字为本报告的工程判断，引用作者没有给框架这些分数。一个分差不能解释成20%的量化优势。

分值 含义
5 有直接且可组合的常用机制，该项额外建设较少
4 有可复用实现路径，仍有配置、适配或使用限制
3 有基础机制或集成路径，需要明显的应用组合
2 主要由应用或基础设施负责，专门支持有限
1 已确认主要能力有明显缺口；本版不因未找到文档而给1分
U 证据不足或必须同场实测；不是0分，也不代表不支持

N 表示框架或同项目SDK；E 表示额外包、协议SDK或服务；A 表示应用自建或治理。4N+E表示原生机制加扩展，2A表示主要应用责任。E不一定收费，N也需要配置。

证据分为：D（官方文档/源码）、T（局部实测）、U（待验证）。每个比较点给出对应来源与验收方法；完整测试状态集中列在代码章。配置合理并不证明生产安全，接口存在并不证明性能达标。

本版共16类64项。不计算无场景总分；权限、业务正确性等硬约束不能靠其他高分抵消。计算项目权重时还要防止重复计算：checkpoint与短期记忆、流程控制与多Agent、streaming与UI交互之间有关联。

常用术语

  • Checkpoint / state / run：分别指执行记录、运行状态和一次任务；checkpoint保存了什么、何时保存，要以具体实现为准。
  • MCP（Model Context Protocol）/ SDK（Software Development Kit）：前者用于模型应用接入工具和资源，后者是开发接口与库；接口兼容需按版本确认。
  • HITL（Human-in-the-loop）/ AI2UI：前者是运行中由人补充或确认，后者在本文泛指Agent与界面交互；A2UI是其中一种具体界面协议。
  • RAG（Retrieval-augmented generation）/ tracing / provider：分别是检索后生成、记录调用链、具体模型供应商或适配实现。
  • P95 / RSS / GIL：分别是95%样本不超过的时延、进程驻留内存、CPython解释器锁；三者不能互相替代评价系统性能。
  • RPO / RTO：分别表示故障恢复可接受的数据损失时间范围、恢复服务所需时间目标。

生命周期能力分析

本章按工程主题展开。每个评分项的验收方法均为建议执行的办法；只有代码章标为实测的局部行为已经执行。

A 开发体验

先看开发者如何写代码和定位错误。简单Agent的起步成本，与复杂系统的可控制程度，应分别比较。

对选型的影响： 普通循环优先LangChain；代码中的业务函数在四种框架中都应独立于运行时。

A1 简单 Agent 的起步成本

完成一次模型调用、一次工具调用，并拿到最终回答，需要搭建多少基础代码。

  • LangChain · 5N： create_agent 封装常见模型—工具循环，简单任务代码少；复杂流程仍需理解运行机制。

  • LangGraph · 3N： 通常要先定义 state、node、edge；起步代码较多，换来对流程的直接控制。

  • Google ADK · 4N： Agent、Runner 和工具定义形成统一入口；先理解 session 与 event 才容易排查运行问题。

  • Eino · 4N： ChatModelAgent 和 Go 工具接口可快速组合；泛型、错误处理使代码比 Python 示例显式。

依据：S04、S05、S19、S27。

建议验证： 由熟悉各语言的开发者完成同一小任务，分别记录开发与排错时间，不能只数代码行。

代码与范围： C01–C04。

A2 数据类型与输入校验

是否能提前发现字段缺失、类型错误；模型输出是否还需在运行时验证。

  • LangChain · 4N： 工具参数和结构化输出可用类型定义与 Pydantic；类型正确仍不代表业务含义正确。

  • LangGraph · 4N： state 可用 TypedDict/Pydantic 等描述；TypedDict 本身不会替所有节点做运行时校验。

  • Google ADK · 4N： Python 的模型和工具 schema 提供结构约束，外部输入仍需业务校验。

  • Eino · 4N： Go 泛型和 struct 可在编译期发现接口不匹配；JSON 与模型生成内容仍需运行时校验。

依据：S40、S41、S42、S43。

建议验证： 分别提交缺字段、错误类型、越界数值和额外字段，观察拒绝位置。

代码与范围： C02/C04/C05。

A3 扩展与拦截点

能否在模型、工具调用前后统一插入校验、日志或替换逻辑。

  • LangChain · 5N： middleware 直接覆盖常见 agent loop 环节，适合统一策略。

  • LangGraph · 4N： 可用节点、包装器和 runtime context；通用策略放在哪个边界需团队约定。

  • Google ADK · 4N： callbacks/plugins 提供扩展入口，应确认当前使用的 Agent/Workflow 路径都经过这些入口。

  • Eino · 4N： callback 和 ADK middleware 可扩展；不同版本的 state 改写时机需要回归。

依据：S40、S42、S44、S30。

建议验证： 正常、重试、resume 和子 Agent 四条路径都必须经过同一策略。

代码与范围： C05；各框架挂接位置依所选 API 配置。

A4 业务代码与框架解耦

以后换框架或升级时，业务规则能保留多少。

  • LangChain · 3A： 工具函数可以独立，但 middleware 与消息类型容易扩散到业务代码。

  • LangGraph · 3A： 图节点可调用普通函数；state 和 checkpoint 格式仍会形成框架依赖。

  • Google ADK · 3A： 可把业务实现置于普通函数中；若业务直接依赖 ToolContext/Session，迁移成本增加。

  • Eino · 3A： 用普通 Go 接口和 context 包装业务逻辑较直接；compose/adk 类型仍应限制在接入层。

依据：S04、S42、S44、S43。

建议验证： 选一条业务规则，在不启动框架的测试里运行；再估算更换消息/状态类型需要改多少文件。

代码与范围： C05 是框架外的普通函数示例。

B 模型与工具接入

模型、MCP与HTTP工具是最容易复用生态的地方，也最容易出现“聊天可用、工具调用不兼容”的情况。接口存在和目标组件通过测试是两层证据。

对选型的影响： 已有adapter满足模型与协议时优先复用；缺少目标能力会推翻其他维度的优势。

B1 模型供应商与本地模型

切换模型时能否复用接口，以及流式、tool calling 等能力是否一致。

  • LangChain · 4E： 统一模型接口和 provider packages 可复用；每种模型能力仍不同。

  • LangGraph · 4E： 可直接调用模型 SDK，或复用 LangChain provider packages；可复用接口，实际兼容范围仍需按模型验证。

  • Google ADK · 4N+E： 支持多个模型接入路径；Google 模型之外的功能需按 adapter 验证。

  • Eino · 4E： ChatModel 接口与 eino-ext 提供适配；必须核实所选模型的具体参数及事件支持。

依据：S45、S05、S17、S31。

建议验证： 对目标模型逐项测试工具调用、流式、usage、超时、错误码，而不只测试普通聊天。

代码与范围： C01 用本地 stub，仅证明工具循环，不证明真实模型兼容。

B2 Structured output

模型是否能按指定 schema 返回数据，失败后是否易于处理。

  • LangChain · 5N+E： 提供 provider/tool 两类结构化策略及验证入口；底层模型支持条件仍影响结果。

  • LangGraph · 4E+A： 节点可使用模型结构化接口并做显式验证；图的 state 类型不自动约束模型文本。

  • Google ADK · 4N+E： LlmAgent 的结构化配置可用；同时使用 tools、schema 与具体模型时需要组合测试。

  • Eino · U： Go 解码和工具 schema 能构成实现基础；尚未核对目标provider的原生schema约束、错误重试和tools组合，不作相对完整度评分。

依据：S41、S45、S43、S57。

建议验证： 测试错误 JSON、合法 JSON 但缺字段、超长输出、拒答，以及 tools+schema 同时开启。

代码与范围： C02 展示业务输入验证；不冒充模型 Structured output DEMO。

B3 MCP 接入

能否列出远端工具、调用工具，并传递调用上下文。

  • LangChain · 4E： langchain-mcp-adapters 可把 MCP 工具接入 agent；连接生命周期要配置。

  • LangGraph · 4E： 复用相同 adapter 或直接 SDK；不必自行实现协议，但需自己控制节点与上下文。

  • Google ADK · 4N+E： 官方 MCP 工具路径存在；版本、transport 和用户凭据要逐项验证。

  • Eino · 4E： eino-ext 有 MCP 适配；SDK 变体与 _meta 行为需对照实际依赖。

依据：S10、S31、S58。

建议验证： 测试 Streamable HTTP、工具清单刷新、重连、取消、错误返回、每请求身份，不能只看 tools/list 成功。

B4 普通 API / OpenAPI 接入

已有 HTTP API 转成工具，需要多少手工描述和业务适配。

  • LangChain · 3E+A： 可以把函数/HTTP 调用包装成工具；自动导入能力要按集成包评估。

  • LangGraph · 3E+A： 图可调用任意 HTTP 客户端；本身不承担 OpenAPI 文档治理。

  • Google ADK · 4N+E： 有官方 OpenAPI 工具路径，可减少基础描述工作；认证及响应语义仍要验证。

  • Eino · 3E+A： Go 函数封装工具直接；声明导入、分页和风险审核通常仍由应用承担。

依据：S10、S42、S59、S43。

建议验证： 导入带分页、认证、枚举、oneOf 的同一 API，检查 schema 保真和错误表达。

代码与范围： C01 的普通函数工具仅展示接入入口。

C 流程控制

流程控制决定哪些步骤必须执行、并行结果如何合并、子Agent看到哪些信息。多Agent数量不直接代表质量。

对选型的影响： 显式复杂流程推荐LangGraph；ADK Workflow和Eino compose同样应进入备选验证。

C1 分支、循环与确定性步骤

哪些步骤必须做、做完走哪一条路，能否在代码中明确表达。

  • LangChain · 3N+E： 常见 agent loop 已封装；任意复杂业务拓扑通常要进入 LangGraph。

  • LangGraph · 5N： StateGraph 直接定义节点和边，便于审查分支和终止条件。

  • Google ADK · 5N： 2.x Workflow 已有显式图，不能按早期版本认定其没有图编排。

  • Eino · 5N： compose Graph/Workflow 可以直接表达确定性步骤，适合与 Go 业务函数组合。

依据：S40、S42、S19、S60。

建议验证： 检查模型给出错误建议时，强制校验步骤仍不会被跳过。

代码与范围： C02/C03/C04。

C2 并行执行与结果合并

多个步骤能否同时运行；写同一份状态时冲突怎么处理。

  • LangChain · 3N+E： 工具可以并行，复杂 fan-out/fan-in 更适合下沉到图。

  • LangGraph · 5N： 并行节点与 reducer 能明确合并规则；错误 reducer 仍可能覆盖结果。

  • Google ADK · 4N： Parallel Agent 和 graph 路径可表达并行；共享状态及合并规则要明确。

  • Eino · 4N： 图分支和并行 Agent 可用；共享对象仍须遵守 Go 并发安全约束。

依据：S42、S19、S27、S60。

建议验证： 让两个分支同时写状态，再让其中一个失败，检查结果与重试行为。

代码与范围： C08 的并发任务实验不是单图 fan-in 验证。

C3 多 Agent 分工

能否按角色拆分任务，并控制交接、子任务生命周期。

  • LangChain · 4N+E： 提供多 Agent 组合模式；多角色不自动提高质量，要衡量额外调用。

  • LangGraph · 5N： 子图可明确分工、状态边界与返回路径，控制细但需要设计。

  • Google ADK · 5N： Agent tree、工作流及协作能力是主要设计内容，适合统一 Runner 管理。

  • Eino · 4N： ADK 有子 Agent、AgentTool 等路径；应按所选模式验证消息交接。

依据：S46、S42、S19、S27。

建议验证： 同一问题对比单 Agent 与多 Agent 的成功率、token 和时延，避免只展示角色数量。

C4 Agent 之间的上下文隔离

一个子 Agent 是否只看到它需要的信息，能否避免历史不断膨胀。

  • LangChain · 4A+E： 可显式构造子 Agent 输入；不能默认把所有 history 原样转发。 S46

  • LangGraph · 4N+A： 子图 state 和输入映射让信息边界显式；是否泄露共享state仍取决于应用输入与授权设计。 S42

  • Google ADK · 4N+A： 可通过 session、state 和子 Agent 输入策略控制；要区分共享和局部信息。 S22

  • Eino · 4N+A： AgentTool默认只接收模型生成的请求参数，完整history需要显式启用；特定Workflow Agent会共享上下文，应按协作模式选择。 S72、S67

依据：S46、S42、S22、S67、S72。

建议验证： 给一个子 Agent 填入仅它可见的标记，断言其他子 Agent 的模型输入中没有该标记。

代码与范围： C05 展示身份校验；不代替模型消息隔离测试。

D 状态与恢复

运行状态保存、用户等待、崩溃重试与升级恢复应分别核对。外部API成功但运行记录尚未提交，是所有路线都要处理的窗口。

对选型的影响： 细粒度恢复是LangGraph的主要推荐理由；业务幂等、防重和对账仍需单独设计。

D1 Checkpoint 持久化

进程退出以后，是否还能读回执行状态；何时写入存储。

  • LangChain · 5N+E： create_agent 依赖 LangGraph checkpointer，具备持久化基础；配置内存 saver 不算持久。 S04、S06

  • LangGraph · 5N+E： super-step 与 pending writes 的保存契约明确，可接持久 saver。 S06

  • Google ADK · 4N+E： Session/Event与resume提供恢复路径；官方文档对工具重复、自定义Agent、Web/CLI有明确限制。2.x Workflow组合未在本次验证。 S21

  • Eino · 3N+A： 有中断保存与CheckPointStore，store由使用者实现；v0.9.21普通图运行不是默认每个完成节点都持久保存。中断恢复不等于任意强杀后的逐步恢复。 S28、S73

依据：S04、S06、S21、S28、S73。

建议验证： 分别在正常步骤后、人工等待中、工具调用中强杀，核对最后可恢复位置。

代码与范围： C07：真实 LangGraph 持久恢复代码与原始结果。

D2 崩溃重放与副作用防重

恢复会重复哪些代码，能否避免重复扣款、发消息或执行操作。

  • LangChain · 3N+A： 继承底层恢复机制；外部副作用仍需要业务幂等。

  • LangGraph · 3N+A： 重放位置有明确语义；工具成功而 checkpoint 未提交的窗口仍需下游幂等。

  • Google ADK · 3N+A： 官方 resume 明确工具可能运行多次，应自行避免重复副作用。

  • Eino · 2A： 中断类型影响重入；外部操作结果和 checkpoint 不天然处于同一事务。

依据：S07、S21、S28。

建议验证： 在远端提交后、状态提交前终止进程；必须能查询结果、防重或进入明确的不确定状态。

代码与范围： C07：effect_attempt=2，但模拟下游唯一操作只提交1次。

D3 Human-in-the-loop

中途请求人补充、修改或批准，之后能否继续。

  • LangChain · 5N+E： HumanInTheLoopMiddleware 适合工具审批和编辑；完整恢复仍需 durable saver。

  • LangGraph · 5N+E： interrupt/Command 可传结构化数据，适合多字段和业务交互。

  • Google ADK · 4N： RequestInput 与 confirmation 提供交互入口；API/语言之间恢复细节不完全相同。

  • Eino · 4N+A： 支持定向中断和带数据恢复；交互记录、有效期与 renderer 需要应用维护。

依据：S61、S07、S20、S27。

建议验证： 测试批准、拒绝、修改、多中断、超时，以及刷新页面后继续。

代码与范围： C02/C03/C07。

D4 执行历史、回放与版本升级

能否查看过去状态；旧任务能否在新代码下恢复。

  • LangChain · 4N+A： 可用底层状态历史，但业务版本兼容仍自行管理。

  • LangGraph · 4N+A： 提供历史与 time travel；回放不撤销真实外部操作，也不保证任意改图兼容。

  • Google ADK · 3N+A： 有 session/event 历史；resume 文档对停止后修改工作流有明确限制。

  • Eino · 3N+A： 有状态序列化和迁移相关能力；类型、图结构及 middleware 语义变动要回归。

依据：S06、S21、S30、S74。

建议验证： 用旧版本生成挂起任务，再升级节点/schema，验证兼容、迁移或明确拒绝。

代码与范围： C07 是同版本恢复，不是跨版本测试。

E 用户交互

对选型的影响： 复杂交互推荐图编排加UI协议；仅有固定表单时，高层Agent入口也可满足需求。

E1 Streaming 与自定义事件

能否逐步显示文本、进度、状态和工具执行结果。

  • LangChain · 5N： Agent 可流式输出消息与状态，需前端适配具体事件格式。

  • LangGraph · 5N： 提供多类流式事件，便于把图状态与业务进度分开。

  • Google ADK · 4N： Runner/Event 提供流式路径；要定义用户可见与内部诊断事件的边界。

代码与范围： C08 涉及运行，不证明前端 Streaming 已接通。

E2 动态表单与 Generative UI

Agent 能否要求填写多个字段、展示图表和可交互组件。

  • LangChain · 4E+A： 可通过 UI adapter 和工具/交互载荷生成组件；不是 create_agent 自带网页。

  • LangGraph · 4N+E+A： 结构化 interrupt 和自定义事件适合关联表单，renderer 与 catalog 另外实现。

  • Google ADK · 4N+E+A： RequestInput 携带输入需求，可连接交互层；开发 UI 不等于完整生产 UI。

依据：S33、S35、S20、S32。

代码与范围： C02 是结构化输入；C05 是应用事件校验，无 renderer。

E3 前端操作与受控页面跳转

能否打开详情页、更新筛选条件，且不能执行任意前端代码。

  • LangChain · 3E+A： 可接前端工具事件；页面路由和允许操作由宿主管理。

  • LangChain · 2A： 恢复运行依赖底层存储备份；业务防重账本与checkpoint必须一起规划。

  • LangGraph · 2A： checkpointer提供运行快照，数据库备份与跨区恢复是另一层责任。

  • Google ADK · 2A： SessionService后端和artifact后端需分别备份，恢复后验证run与event关联。

  • Eino · 2A： CheckPointStore接口不负责数据库灾备；外部资源实际状态还需对账。

Checkpoint、幂等与事务

checkpoint 是运行状态记录。外部 API 操作可能已经成功，但框架还没保存下一条记录，进程便退出。恢复后同一步可能再次执行。解决方法取决于外部系统：可用稳定的 idempotency key、防重表、outbox，或读取实际状态后做 reconciliation。框架恢复和业务事务之间没有天然的跨系统原子性。

等待用户时还要处理重复提交、过期表单、权限变更和两个 worker 同时恢复。这些是 D2、E4、F1/F2 与 I3 的交叉验收事项，不应分别得分后就假定组合一定正确。C07 专门展示了“调用尝试两次、业务记录一次”的区别。

依据：S06 Checkpointers；S07 Interrupts；S21 ADK resume；S27 Eino HITL；S28 Eino checkpoint 手册；本地证据：附件 C07。

GIL、异步与多租户

默认 CPython 的 GIL 限制同一进程中 Python 字节码的线程并行，不会把正确使用 async 的网络等待全部串行化。相反，把纯 Python 的重计算或阻塞 SDK 放进 event loop，会阻塞其他任务；需要转到合适的线程、进程或外部 worker，具体取决于代码是否释放 GIL。

Go 的 goroutine 提供不同的并发实现方式，但模型等待、数据库写入、连接池和供应商限额仍可能成为瓶颈。容器解决运行环境交付问题，不会自动解决 CPU 或隔离问题。必须把框架机制、资源占用和多租户公平调度分开评估。

依据：S38 CPython threading；S39 CPython asyncio；S64 Effective Go — concurrency；本地证据：附件 C08。
